После запуска JvmExperience.main() программа выводит приглашение и «засыпает» на 30 секунд, чтобы дать время подключиться.

Строка консоли:

Please open 'ru.netology.JvmExperience' in VisualVm

Что происходит в JVM: Главный поток main приостановлен вызовом Thread.sleep(30_000).
На графиках VisualVM: В этот момент графики Heap, Metaspace и Classes стабильны. Загружены только базовые классы JDK и самого приложения (около 500 классов).

2. Загрузка классов в Metaspace
Программа начинает сканировать пакеты с помощью библиотеки Reflections и загружать классы в память.

Строки консоли:

[время]: loading io.vertx
[время]: loaded N classes
[время]: loading io.netty
[время]: loaded N classes
[время]: loading org.springframework
[время]: loaded N classes

Что происходит в JVM: Классы из указанных библиотек загружаются ClassLoader'ом в область памяти Metaspace. Это долгая и ресурсоёмкая операция.
На графиках VisualVM:

Classes: Ступенчатый рост вверх. Каждая ступенька — это новая библиотека (сначала Vert.x, потом Netty, потом Spring).

CPU usage: Заметный скачок вверх, так как загрузка и сканирование классов нагружают процессор.

Metaspace: Резкий рост (если переключиться на вкладку Metaspace).

3. Создание объектов в Heap
После загрузки классов программа переходит к созданию объектов.

Строки консоли:

[время]: now see heap
[время]: creating 5000000 objects
[время]: created

Что происходит в JVM: В куче (Heap) создаются 5 миллионов объектов SimpleObject. Все они сохраняются в списке List<SimpleObject>, поэтому на них есть ссылки, и сборщик мусора не может их удалить.
На графиках VisualVM:

Heap: Резкий, почти вертикальный рост. Память заполняется объектами.

CPU usage: Пиковая нагрузка (почти 100%), так как создание миллионов объектов требует ресурсов.

GC activity: Низкая, так как объекты достижимы (мусора пока нет).

Программа повторяет создание ещё дважды (simpleObjects.addAll(...)). На графике Heap это выглядит как «пила»: память заполняется, затем может сработать Minor GC (если Eden переполнился), снова заполняется.


4. Завершение программы
Когда метод main завершается, все локальные переменные исчезают. На 15 миллионов созданных объектов больше нет ссылок, они становятся мусором.

Что происходит в JVM: Сборщик мусора (Garbage Collector) освобождает память. Поток main завершается.
На графиках VisualVM:

Heap: Резкое падение использования памяти почти до нуля.

Classes: Количество классов может снизиться, если JVM решит выгрузить неиспользуемые классы (хотя Metaspace обычно остается занятым до конца работы JVM).

💡 Вывод
В ходе работы я убедилась, что:

Metaspace увеличивается при загрузке классов и не очищается обычным сборщиком мусора, так как классы остаются в памяти, пока жива JVM.

Heap растёт при создании объектов и очищается сборщиком мусора, когда объекты становятся недостижимыми.

CPU нагружается сильнее всего в моменты активной загрузки классов и создания миллионов объектов.

Графики VisualVM в реальном времени точно отражают этапы выполнения программы, описанные в коде.
